# TaskFlow 第二阶段常见故障定位与排查手册

> 适用范围：用户注册、登录、JWT 认证、Token
> 刷新、退出登录、前端认证状态管理及自动化测试。\
> 目标：遇到故障时，能够判断问题所在层级，找到有效证据，缩小范围，并验证修复结果。

------------------------------------------------------------------------

## 一、建立正确的故障排查思路

遇到问题时，不要马上修改代码，也不要让 Codex
直接重写整个模块。建议遵循以下顺序：

1.  **确认故障现象**：记录具体操作、预期结果、实际结果、HTTP
    状态码和报错信息。
2.  **定位故障层级**：判断问题出在前端页面、Axios
    请求、后端视图、Serializer、认证组件还是数据库。
3.  **查看关键证据**：检查浏览器 Network、Console、Django 终端、MySQL
    日志和测试输出。
4.  **缩小故障范围**：逐层验证，不要同时修改多个模块。
5.  **最小化修复**：只修改导致故障的代码，避免破坏已完成的认证功能。
6.  **回归测试**：验证故障场景及其关联功能，确认没有引入新问题。

## 二、HTTP 状态码：第一判断依据

  状态码    含义               优先检查
--------- ------------------ ---------------------------------------
  200       请求成功           响应数据是否正确
  201       创建成功           注册数据是否正确保存
  400       请求数据有问题     Serializer、字段验证
  401       身份认证失败       Access Token、Refresh Token、认证配置
  403       权限不足           Permission、账号状态、权限规则
  404       接口不存在         URL 路由、请求地址
  405       请求方法不允许     GET/POST 是否匹配
  500       后端内部错误       Django 终端 Traceback、数据库异常
  502/503   网关或服务不可用   代理、后端服务、部署配置

**特别注意：401 和 403 不能混为一谈。** 401 表示没有通过身份认证；403
表示身份已经识别，但不允许执行当前操作。具体行为也受认证类和权限类配置影响。

## 三、第二阶段高频故障排查

### 1. 注册模块

----------------------------------------------------------------------------------------------
  故障现象                 可能原因                                 定位位置
------------------------ ---------------------------------------- ----------------------------
  用户名重复仍然注册成功   Serializer 检查或数据库唯一约束缺失      `RegisterSerializer`、User
                                                                    模型

  邮箱重复没有拦截         邮箱检查逻辑不正确                       `validate_email()`

  两次密码不一致仍然通过   对象级验证没有执行                       `validate()`

  密码以明文保存           错误使用 `objects.create()`              `create()`

  User 创建成功，Profile   事务配置或异常处理不正确                 `transaction.atomic()`
  创建失败                                                          

  并发注册出现重复错误     只使用                                   Serializer、数据库
                           `exists()`，没有处理数据库唯一约束冲突   
  ----------------------------------------------------------------------------------------------

重点代码：

``` python
User.objects.filter(username__iexact=value).exists()
```

检查用户名是否已存在。

``` python
User.objects.create_user(
    username=username,
    password=password
)
```

使用 `create_user()` 确保密码经过哈希处理。

``` python
with transaction.atomic():
    ...
```

确保相关数据库操作一起成功或一起回滚。

**排查原则：** `exists()`
负责提前检查，数据库唯一约束负责最终保证，`IntegrityError`
负责处理并发竞争。捕获 `IntegrityError`
时，应在事务边界外处理，并尽量识别具体约束，避免把所有数据库错误都误报为用户名重复。

### 2. 登录模块

--------------------------------------------------------------------------------------
  故障现象                可能原因                               定位位置
----------------------- -------------------------------------- -----------------------
  正确密码返回 401        用户名、密码或账号状态不符合认证条件   LoginSerializer、User

  返回 400                请求字段缺失或格式错误                 Network Request Payload

  登录接口 404            URL 配置错误                           `urls.py`

  登录成功但没有 Token    Serializer 返回数据或视图响应异常      LoginAPIView

  登录成功但页面不跳转    前端登录流程或 Router 问题             `useLogin.js`、router

  登录后立即显示未登录    Token 未保存或 `/me/` 请求失败         `token.js`、`auth.js`
  --------------------------------------------------------------------------------------

登录完整流程：

1.  `Login.vue` 收集账号密码。
2.  `login()` 调用后端登录接口。
3.  `LoginAPIView` 验证账号密码。
4.  SimpleJWT 签发 Access Token 和 Refresh Token。
5.  前端保存 Token。
6.  `getCurrentUser()` 请求 `/me/`。
7.  Pinia 保存用户信息。
8.  跳转 Dashboard。

如果登录接口返回 200，但页面没有进入
Dashboard，应该优先检查前端，不要直接修改后端登录逻辑。

### 3. JWT 认证模块

常见故障：登录成功，但访问受保护接口返回 401。

首先检查浏览器 Network：

1.  登录接口是否返回 Access Token？
2.  Token 是否成功保存到 `sessionStorage`？
3.  请求是否携带 Authorization？
4.  Authorization 格式是否正确？
5.  Django 是否配置 JWTAuthentication？
6.  Token 是否过期或被撤销？
7.  当前用户是否被禁用？

正确请求头：

``` http
Authorization: Bearer <AccessToken>
```

重点检查配置：

``` python
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    ],
}
```

  观察结果                        优先怀疑
------------------------------- --------------------------------------
  Token 不存在                    登录流程、Token 存储
  请求头没有 Bearer               Axios 请求拦截器
  `/me/` 返回 401                 JWT 验证、Token 有效性
  `/me/` 返回 200，工单接口 401   工单接口认证配置、视图特殊处理
  Token 未过期但 401              用户状态、签名、Token 类型、认证配置
  返回 403                        权限类、账号状态及业务权限

### 4. Token 自动刷新模块

预期流程：

``` text
请求业务接口
    ↓
Access Token 失效
    ↓
后端返回 401
    ↓
Axios 响应拦截器捕获 401
    ↓
Refresh Token 请求刷新接口
    ↓
后端返回新 Access 和 Refresh
    ↓
保存两个新 Token
    ↓
重新发送原请求
    ↓
业务接口返回成功
```

常见问题：

  故障                            排查方向
------------------------------- ------------------------------------------
  401 后没有刷新                  响应拦截器是否生效
  刷新接口返回 401                Refresh 是否过期、拉黑或类型错误
  刷新成功但原请求仍 401          重试请求是否携带新 Access
  并发请求重复刷新                是否使用共享 Promise 锁
  刷新成功但旧 Refresh 仍被使用   是否同时保存新 Refresh
  页面不断刷新 Token              是否存在重试递归或错误的 401 处理
  迟到 401 导致再次刷新           是否比较 `_accessTokenUsed` 和当前 Token

三个关键保护机制：

-   **`_retry`**：避免同一个请求无限重试。
-   **`refreshPromise`**：多个并发请求共享同一次刷新。
-   **`_accessTokenUsed`**：识别迟到的旧 Token 请求，避免重复刷新。

### 5. 退出登录模块

排查时区分两个动作：

  动作                     作用
------------------------ -------------------------------
  后端撤销 Refresh Token   阻止该 Refresh Token 继续刷新
  前端清理本地认证状态     清除 Token 和 Pinia 用户信息

TaskFlow 的退出逻辑应做到：

1.  提交当前 Refresh Token。
2.  后端尝试将 Refresh Token 加入黑名单。
3.  前端清除本地 Access 和 Refresh Token。
4.  清除 Pinia 中的 `user`。
5.  跳转登录页。

**注意：** 退出登录后，旧 Access Token
可能仍然有效至自身过期。这不代表退出操作完全失败。

### 6. Vue、Pinia 与路由模块

  故障现象                           排查位置
---------------------------------- -------------------------
  页面白屏                           Console、Vue 组件错误
  `/dashboard` 显示 No match found   Router 路由表
  刷新页面后自动退出                 `initializeAuth()`
  登录后仍显示未登录                 Pinia 状态更新
  已登录访问登录页仍停留             `guestOnly` 守卫
  未登录访问 Dashboard 仍能进入      `requiresAuth` 守卫
  页面显示旧用户信息                 `clearAuth()`
  多个初始化请求重复调用 `/me/`      初始化 Promise 共享机制

**Pinia 中的 `isAuthenticated` 只是前端状态，不是后端身份认证的依据。**
后端仍然必须通过 JWT 验证请求。

### 7. 自动化测试模块

------------------------------------------------------------------------
  故障现象                            可能原因
----------------------------------- ------------------------------------
  测试无法创建数据库                  MySQL 测试库权限

  测试数据库连接失败                  数据库配置、用户权限

  测试通过但浏览器失败                测试环境与真实请求流程不同

  测试使用了错误用户                  `setUp()` 数据准备不正确

  Token 测试通过但真实 JWT 失败       使用了
                                      `force_authenticate()`，没有走真实
                                      JWT 认证

  迁移检查失败                        模型变更没有生成迁移文件
  ------------------------------------------------------------------------

``` powershell
python manage.py check

```

## 四、浏览器与后端的排查工具

### 1. Chrome DevTools → Network

查看请求地址、请求方法、Authorization、Request Payload、Response
和状态码。最适合定位前后端接口问题。

### 2. Chrome DevTools → Console

查看 Vue 运行错误、JavaScript 异常、Router
警告和请求错误。最适合定位白屏和页面不跳转。

### 3. Django 终端

查看 Traceback、Serializer 异常、认证失败和数据库错误。最适合定位后端
500。

### 4. MySQL 客户端

检查用户权限、表结构、唯一约束、外键和数据库数据。最适合定位数据层问题。

## 五、真正排查问题时的标准流程

-   [ ] 复现问题并记录具体操作。
-   [ ] 打开 Network 确认请求地址和 HTTP 状态码。
-   [ ] 检查 Request Headers 和 Payload。
-   [ ] 检查 Response 响应内容。
-   [ ] 检查 Console 是否有前端错误。
-   [ ] 检查 Django 终端 Traceback。
-   [ ] 检查相关 Serializer、View 和认证配置。
-   [ ] 检查数据库状态和约束。
-   [ ] 确定唯一根因后进行最小修复。
-   [ ] 重新测试故障场景和关联功能。

## 六、给 Codex 的故障排查指令模板

不要只对 Codex 说"帮我修复这个错误"。建议使用下面的模板：

``` text
请对 TaskFlow 当前故障进行系统性排查。

项目目录：F:\\Demo\\TaskFlow

故障现象：
【在这里描述具体错误】

复现步骤：
【写出操作顺序】

实际结果：
【写出实际表现】

预期结果：
【写出期望表现】

排查要求：

1. 先定位故障所属层级：Vue、Axios、Pinia、Django View、Serializer、JWT、MySQL 或 Router。
2. 检查相关源码和调用链。
3. 根据实际错误信息寻找根因，不要凭猜测修改代码。
4. 先输出根因、证据、影响范围和修复方案。
5. 优先最小化修改，不要重构无关模块。
6. 不要删除已有功能，不要重置数据库，不要随意修改迁移文件。
7. 修复后运行相关自动化测试和生产构建。
8. 输出修改文件、修改原因、测试结果和仍存在的风险。

特别要求：请解释为什么出现这个问题，以及今后应该如何独立定位同类问题。不要只给出修改后的代码。
```

## 七、第二阶段最需要牢固掌握的知识

  核心知识          应达到的水平
----------------- -----------------------------------
  Serializer 验证   能区分字段验证、对象验证和 create
  数据库事务        能解释 atomic 和回滚
  JWT 认证          能讲清 Access、Refresh 和认证流程
  Axios 拦截器      能独立追踪请求和响应
  Token 轮换        能解释双 Token 更新和黑名单
  Pinia             能区分本地状态和后端身份
  Router 守卫       能解释登录状态恢复与页面访问控制
  自动化测试        能定位测试失败原因
  权限安全          能识别用户身份伪造和越权访问

## 八、学习建议

先把这份手册作为第二阶段的故障排查资料。之后通过真实故障案例练习，逐渐从"知道是什么"提升到"能够自己定位和修复"。

建议下一步进行一次第二阶段模拟故障排查：通过真实风格的报错日志，练习判断故障层级、定位证据和提出修复方案。
